# HerFuture AI Web Builder

## Purpose

Create a usable, accessible, mobile-friendly website that helps girls and women discover technology learning resources, free courses, open-source opportunities, AI-assisted career guidance, and stories shared by women in tech. Support English and Hausa. Prefer simple HTML, CSS, and JavaScript so beginner contributors can understand and maintain the code.

## When to use this skill

Activate for requests to build the HerFuture AI website, add or change a HerFuture AI feature, improve its design or accessibility, translate its interface, or add verified technology-learning resources.

Do not activate for unrelated websites or general career advice that does not involve building or maintaining this project.

## Gather first

Before coding, identify any details that materially affect the implementation:

- Which page or feature is requested, and what should a visitor be able to do?
- Is the request for a new site, an update to existing files, or a bug fix? Inspect available project files before deciding.
- Which language should be shown first, English or Hausa? Keep a clear language switch available when both are supported.
- Are there supplied, verified resource URLs, approved copy, branding, or women’s stories to use?
- Does the feature need a backend, external AI service, user accounts, or data storage? Explain any infrastructure or privacy implications before implementing it.

If a detail is not essential, choose a simple, reversible default and state the assumption. Do not ask questions already answered in the conversation or project files.

## Step-by-step process

1. **Inspect before editing.** Review the existing files, current design, available dependencies, and repository instructions. Preserve working functionality and avoid replacing unrelated work.
2. **Plan the smallest useful change.** Describe the page or behavior briefly. Use semantic HTML, plain CSS, and vanilla JavaScript unless the user explicitly requests a different stack.
3. **Build the core experience.** Include clear navigation and useful sections for learning resources, career guidance, open-source opportunities, and women’s tech stories. Use a responsive layout that works on small phone screens and larger displays.
4. **Support English and Hausa.** Put interface text in a maintainable translation dictionary or equivalent structure. Translate interface copy carefully; do not claim fluent or culturally validated Hausa unless it has been reviewed by a fluent speaker. Keep language choice accessible and predictable.
5. **Keep information trustworthy.** Use only supplied or verifiable resources. For each external opportunity or course, preserve its actual name, source URL, eligibility, and date details only when verified. If verification is unavailable, mark the item as needing verification or leave it out. Never invent statistics, scholarships, deadlines, partners, testimonials, or URLs.
6. **Implement AI honestly.** If AI career guidance is requested, first determine whether a real model or API is configured. Do not fake an AI response with hard-coded text or label a rule-based demo as AI. If no model is configured, build a clearly labelled prototype or interface and explain what backend, model, privacy notice, and configuration are still needed. Never expose API keys in browser JavaScript.
7. **Protect people and their stories.** Do not publish personal stories, names, photos, contact details, or identifying information without clear permission. For story submissions, explain where submissions go and who can see them. Do not imply a form stores or sends data unless that behavior is implemented and tested.
8. **Make it accessible.** Use semantic landmarks, a logical heading order, visible keyboard focus, labels for form fields, sufficient contrast, descriptive link text, and meaningful alternative text. Do not rely on color alone. Respect reduced-motion preferences when adding animation.
9. **Test the result.** Run available checks. At minimum inspect links, language switching, form validation, browser-console errors, and narrow-screen layout. If a browser or automated test environment is unavailable, say what could not be tested and give the user simple manual test steps.
10. **Explain the handoff.** Summarize files changed, how to run the site locally, what was tested, any known limitations, and the next step for a beginner contributor.

## Output format

Deliver:

1. The complete changed website files, not just fragments, unless the user explicitly asks for a snippet.
2. A short feature summary and any assumptions.
3. Setup and run instructions suitable for a beginner. For a static site, explain how to open `index.html` and recommend a local development server if browser behavior requires one.
4. Test results, including failed or skipped checks.
5. A short accessibility and mobile-readiness note.
6. A list of any content, links, AI integration, or backend work that still needs verification or implementation.

## Rules and boundaries

- Prefer plain HTML, CSS, and JavaScript and avoid unnecessary frameworks, build tools, and dependencies.
- Do not invent facts, sources, URLs, opportunities, women’s stories, partner endorsements, impact numbers, or AI functionality.
- Do not claim a feature works until its behavior has been implemented and checked.
- Do not collect sensitive personal information without a clear need, explicit explanation, and appropriate safeguards.
- Do not commit credentials, API keys, private user submissions, or personal data to a public repository.
- Use user-provided images and content only as permitted. Add attribution or license notes when required.
- Do not promise that the site guarantees employment, scholarships, safety, or career outcomes.
- Keep language respectful, welcoming, and appropriate for girls and women with little or no technical experience.
- If a request conflicts with these rules or needs unavailable facts, explain the limitation and offer a safe, honest alternative.
